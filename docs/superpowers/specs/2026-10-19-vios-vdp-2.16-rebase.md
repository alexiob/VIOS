# VIOS VDP rebase evaluation: vendored VDP 1.04 against agon-vdp 2.16.0

**Status:** evaluation only (2026-10-19). No firmware changed, the board was
not touched.

**Context:** The ESP32 firmware (`firmware/esp32-vios`) vendors the Agon VDP
1.04 and vdp-gl 1.0.3, with VIOS changes on top. AgonPlatform agon-vdp
2.16.0 is current. The owner has already decided to update the eZ80 to MOS
3.0.2, which supports VDP 1.04 and up, without waiting for a VDP rebase
(untethered boot spec, `2026-10-19-vios-untethered-boot.md`). This document
answers a separate question: should the vendored VDP be rebased onto 2.16.0?

Hard constraint: the GUI display server (`lib/vios-vds`) composes straight
into the fabgl framebuffer and must keep 60 fps vblank frames
(acceptance on `firmware-untethered-7`: frame work 4.0 ms, vblank start
91 us).

## 1. Inventory: what VIOS changed in the vendored tree

### 1.1 Base

`firmware/esp32-vios/vendor/manifest.json` pins:

|---|---|---|---|

| `vendor/vdp-gl` | `avalonbits/vdp-gl` | `48a0b9a` (2023-04-27) | vdp-gl 1.0.3 |

Build: `espressif32@6.3.0` (arduino-esp32 2.0.x), as upstream 1.04 pins
(its comment: 6.4.0 broke mode 3 by using more memory). App slot limited to

### 1.4 The larger dependency: VIOS code that reaches into the VDP

The 243-line patch (230 added, 13 removed) is what a rebase must re-apply. What it must *re-validate*
is bigger: about 5,000 lines in `include/vios_*.h` and `lib/vios-vds` that
use VDP globals and vdp-gl internals directly, from inside the `video.ino`
translation unit.

| Symbol (uses) | Owner | Used by |
|---|---|---|
| `canvas` (27), `palette` (9), `colourLookup` (3), `videoMode` (8), `ttxtMode` (6), `fontW`/`fontH` (7), `getVGAColourDepth` (7), `set_mode` (4), `plotCharacter`, `processor`, `send_packet` | agon-vdp globals (`graphics.h`, `video.ino`) | `vios_console_vdp.h`, `vios_gui.h`, `vios_g0_probe.h`, `vios_bridge.h` |
| `VDPSerial` (13), `DBGSerial` (8) | agon-vdp | `vios_bridge.h` writes `FA`/`FE`/`FC` packets straight to the UART |
| `VdpRows` → `VGAPalettedController::m_viewPort`, `m_viewPortVisible`, `sgetScanline` (protected) | vdp-gl internals | `vios_console_vdp.h` (4 bpp console blitter), `vios_frame.h`, `vios_gui.h` (`vds_init` gets the row table) |
| `FONT_AGON_DATA` (4) | vdp-gl | `vios_gui.h`, console |
| `vios_vblank_hook` | the vdp-gl patch | `vios_frame.h` |

`VdpRows` is not a vdp-gl edit. It is a subclass cast that reaches protected
members of `VGAPalettedController` to get the framebuffer row table, and it
assumes single buffering (`m_viewPort == m_viewPortVisible`). The whole
4 bpp console and GUI path rests on it. A vdp-gl version that renames,
privatises or double-buffers those members breaks VIOS even when the 21-line
ISR hook re-applies cleanly.

**Observation:** VIOS uses little of the VDP's VDU layer. The GUI composes
into the framebuffer through `vios-vds`, the console renders through its
own blitter, and MOS's output is filtered during the MOS phase. The live
dependencies are the serial transport (`VDPSerial`, `send_packet`, the
stream processor's read functions), the keyboard path, mode setting, and
the vdp-gl VGA16 driver.
