## Findings

No findings requiring a production change.

- Renderer: accepted scrolls require a clean region, update both shadows, block glyph output until viewport restoration, and reject another queued scroll. Composing additional edits or toggling zoom while an operation is queued/partly emitted converges to the same desired screen. Each output slice stays within its budget and 128-byte cap; short-budget fallback splits only at complete VDU commands.
- Cache: IDs `0xFA00`/`0xFA01` are separate, direction-specific entries. Each 19-byte script replacement emits CLEAR before WRITE, matching pinned `video/vdu_buffered.h:184–259` append/call/clear semantics. Miss cost is 39 bytes, hit cost six; reset invalidates CPU cache entries. Scroll amounts use explicit eight-pixel rows, matching pinned `video/vdu_sys.h:487–495`.
- Compositor: plain glyph and cursor-style caches move together. A refused scroll keeps the ordinary reconstruction path. Independent source projection agrees through tabs, CR/LF/CRLF edits, horizontal crops, repeated scrolling, and 54/80-column zoom transitions.
- Runtime: only the captured default deferred binding targeting the captured default native word receives the direct call (`kernel/workbench_runtime.c:59–67`). Shadowed names/replaced hooks retain the 4096-budget observer. Repaint restores the full viewport before clearing; REDRAW retains mode recovery. Ctrl+Space normalization preserves modifier filtering. The fenced diagnostic queries CHAR@ before its end timestamp and before result output; timeout records a paint error recoverable by repaint.
- Transport/build: native TX checks CTS and THRE per byte with a 32-byte cap, preserves IX, counts clear-on-read overrun observations, and returns actual progress. C pauses/collects RX between bursts and opens receive windows on stalls. Baud-specific resident initializer objects, relinking on sidecar mismatch, and ESP embed-time sidecar verification coordinate rates while leaving USB at 115200. The independent USB/ZDI restart path remains outside the VDP transmit lock.

## Addendum — USB bulk-output failure investigation

The parent-owned 384000-internal/115200-USB qualification found a real transport integrity failure. This supersedes any implication that the code review alone qualifies end-to-end deployment. Evidence: `docs/bring-up/vios-fast-display-wire-failure.json` and `docs/bring-up/vios-fast-display-384000.serial.jsonl`. No production source or firmware was changed during this investigation.

### Confirmed observations

- Reconstructed the raw RX byte stream directly from serial JSONL, independently of `ResidentSession` and its COBS decoder. The bad non-boot frame is 134 bytes, compared with 73 earlier identical valid 139-byte frames. The sole difference is deletion of five contiguous bytes `33 30 33 b2 62` at encoded offset 132. Final bytes `fa ca` remain. This establishes a damaged USB-console byte stream; an eZ80 payload error cannot by itself explain the missing precomputed wire CRC bytes.
- The deletion begins exactly at an observed host-read boundary: bad frame starts at raw RX offset 181016, JSONL zero-based row 12354 contains 127 RX bytes ending at offset 181148 (=181016+132); row 12355 receives `fa`, and row 12356 begins `ca 00` followed by the next frame. A read boundary is observable, not proof of which component lost bytes.
- Replayed the original valid frame through `tools/vios_wire.py` split at each of its 140 possible two-chunk boundaries. Every case returns exactly one valid packet with no decoder error. `tools/serial_monitor.py:78–83` logs all bytes returned by pyserial before higher-level parsing; `ResidentSession` history trimming occurs after decoding and does not remove raw log data.
- `usb_send()` (`firmware/esp32-vios/include/vios_bridge.h:52–63`) encodes into a task-local buffer and holds `usb_tx_mutex` across the complete write. The pinned Arduino package is `framework-arduinoespressif32` 3.20009.0. Its `cores/esp32/HardwareSerial.cpp:532–536` calls `uartWriteBuf()` and **unconditionally returns the requested size**. Therefore checking `DBGSerial.write(...) == encoded` would not detect lower-level short/error writes in this package.
- `cores/esp32/esp32-hal-uart.c:429–437` locks the UART and invokes `uart_write_bytes()` while discarding that function's result. HardwareSerial defaults `_txBufferSize` to zero (`HardwareSerial.cpp:139`); no project call enables a TX ring. The pinned `driver/uart.h:507–523` contract says that, with zero TX buffer, `uart_write_bytes()` does not return until the entire request has been sent or pushed into the FIFO. This supports the current stack-buffer lifetime and mutex scope; it does not provide a concrete reason for this five-byte deletion. The ESP UART FIFO is 128 bytes (`soc_caps.h:270`), but offset 132 alone does not establish a FIFO-boundary defect.
- VDP `DEBUG` is zero (`video/video.ino:56`), so `debug_log()` is compiled out. Raw IDF error logging remains configured on UART0 in the pinned SDK, outside the framing mutex; the boot-log failure in the evidence contains such text. That is a known route for **insertion** of unframed bytes, but no such inserted text appears in the bulk-output failure, so it does not explain the observed deletion. Legacy ZDI raw writes are present in vendor source but the normal VIOS loop does not dispatch that legacy command console.

### Discriminating parent-owned bench guidance

1. Repeat the same view-only workload after a clean explicit reboot, retaining every raw RX byte and the resident dropped counter before/after. Keep the USB speed at 115200. Record completed bytes/frames, first error offset and elapsed time; do not treat a failed COBS frame as a source-view mismatch or automatically retry a mutating operation.
2. Compare `WB-VIEW 0 60` with one-row queries that wait for each reply before sending the next. Repeat enough traffic to match or exceed the failed run's 189,971 raw RX bytes. If only continuous output fails, that isolates a sustained-traffic dependency; it does not identify its component. Keeping the reader active after recording a failure preserves evidence and avoids a later host-side overflow caused by stopping reads while the board continues output.
3. Compare the same expected output at each already-authorized internal rate with USB unchanged. The USB UART has no RTS/CTS enabled in the pinned `uartBegin()` configuration. A rate-dependent failure may reflect increased continuous USB occupancy, rather than CPU RX corruption; distinguish these using the resident drop count and raw wire CRC evidence.
4. To identify the failing physical/software boundary, compare a passive capture of ESP GPIO1 UART TX with the received USB bytes for the same COBS frame. Missing bytes already on GPIO1 implicate ESP transmission; intact GPIO1 with damaged USB output implicates the bridge/USB/host side. Without that capture or an equivalent controlled driver/bridge comparison, the current evidence cannot select ESP UART, CH340, USB scheduling, or the macOS serial driver as the concrete cause.

The separate GO/RESUME diagnostic compatibility regression is confirmed by the parent and assigned to the transport worker; it is independent of this byte-loss investigation. No speculative production fix is recommended by this addendum.

## Addendum — final console pacing and frozen recovery ACK review

Reviewed only the final pacing/ACK changes in `firmware/esp32-vios/include/vios_bridge.h` and associated bridge tests. Result: **no actionable correctness or recovery defect found in this patch**. This is not evidence that pacing identifies or eliminates the physical byte-loss cause; the parent's hardware stress results provide that qualification.

- `usb_send()` now holds `usb_tx_mutex` through write, physical UART drain, and `delay(1)` for console-channel frames (`vios_bridge.h:60–69`). This prevents another framed producer from filling the intended gap. The mutex releases between frames of a multi-frame message. Control/event frames add no deliberate drain/delay; they may wait behind the single console frame currently holding the mutex.
- Verified actual pinned Arduino semantics: `HardwareSerial::flush()` calls `uartFlush()`, which invokes `uartFlushTxOnly(uart,true)` (`cores/esp32/esp32-hal-uart.c:440–457`). It waits for `uart_ll_is_tx_idle()`, requiring both FIFO count zero and the transmit state machine idle (`hal/uart_ll.h:773–777`). It does **not** discard RX input. Thus the flush really drains the final stop bit before the delay; host control bytes are not flushed away.
- The UART flush busy-waits under the driver's UART mutex, but UART0 has hardware flow control disabled, so normal drain time is bounded by the bytes already queued at 115200. A largest possible 252-byte frame occupies about 21.9 ms of wire time, plus at most one scheduler-tick interval before the delayed task becomes ready (and any scheduling delay). The normal 128-byte console payload produces a roughly 140-byte frame, about 12.2 ms of wire time. This adds bounded serialization latency to a concurrent control request, rather than a new dependency on the blocked VDP UART. No reverse nested acquisition of the USB frame mutex from a held UART mutex was found in these paths.
- `delay(1)` is `vTaskDelay(1)` with the pinned SDK's `CONFIG_FREERTOS_HZ=1000`. It waits until the next tick, so the actual silent interval can be less than one full millisecond depending on tick phase. The patch's comment promises a scheduler tick, not a guaranteed 1-ms elapsed gap. Hardware interpretation should use the measured behavior rather than assuming an exact millisecond.
- GO and RESUME strings exactly match the frozen baseline, restoring compatibility with inherited raw/resident host consumers. Internal baud remains build metadata, avoiding another ACK-format change.

Verification: `PYTHONPATH=tests .venv/bin/python -m unittest test_wire.WireTests.test_actual_firmware_bridge_boot_control_and_health` passed. It builds/runs the actual bridge under ASan/UBSan at default 1152000, explicit 384000 and 115200; checks console write→flush→delay ordering while the frame mutex is held, complete segmented payload preservation, unchanged control/event scheduling, concurrent frame integrity, and the real Python `ResidentSession`/`ResidentBoard` H/S/Y recovery plus stable GO consumption. Build outputs are temporary. The Serial/RTOS doubles do not model physical UART timing; pinned driver source was inspected separately above. No hardware access or production edits were performed.
